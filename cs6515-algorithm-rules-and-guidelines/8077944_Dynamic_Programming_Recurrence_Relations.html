Dynamic Programming Recurrence Relations

Staff Guidance #10 Dynamic Programming Mathematical Specification
Mathematical rigor, base case rules, directionality, and common pitfalls

This post is a discussion on mathematical notation and the formal nature of recurrence relations in CS6515. This expands upon the solution format detailed in the general DP Guidance.

1. Context

Part 2, or the "recurrence relation", in a DP problem solution for this course provides a rigorous mathematical definition of the table entries for the solution.

  • Part 1 (Subproblem Definition): A short explanation in plain English explaining the conceptual meaning of each table entry.
  • Part 2 (Recurrence Relation): The exact mathematical specification defining table entries recursively.
  • Part 3 (Implementation Analysis): An assessment of the space, fill runtime, and answer extraction for using this table to solve the original problem.

Core Concept: Think of it this way: the recurrence relation is the mathematical specification, and the implementation is the step-by-step algorithm or evaluation order that computes it.

2. What is a Recurrence Relation?

Dynamic Programming fundamentally relies on recurrence relations. Without a recurrence relation, a solution is not a Dynamic Programming solution.

Key Characteristics

  • An Equation: A recurrence relation is an equation, not procedural code.
  • General Rule: The equation provides a general rule for the recurrence.
  • Dependency: The rule defines the next term as a mathematical function of strictly smaller, previous term(s).

Base Cases & Canonical LCS Formulation

To generate the table using the general rule, your rule depends on values being pre-defined for early boundary elements, called base cases. Separate equations are used for base cases. For example, here is the canonical recurrence relation and base cases for Longest Common Subsequence (LCS):

Base Cases:

$$L(i, 0) = 0 \quad ext{for } 0 \le i \le n$$

$$L(0, j) = 0 \quad ext{for } 1 \le j \le n$$

Recurrence:

$$L(i, j) = \begin{cases} \max\{L(i - 1, j), L(i, j - 1)\} & \text{if } x_i \ne y_j \\ 1 + L(i - 1, j - 1) & \text{if } x_i = y_j \end{cases}$$

$$\text{where } 1 \le i \le n, \quad 1 \le j \le n$$

Critical Formulation Rules

  • Multiple Base Cases & Scoped Bounds: Specify index bounds explicitly for indices $i$ and $j$. If no indices are used (such as when there are only one or two individual constant entries like $T[1] = 1$), bounds are not required.
  • Distinct Bounds: The bounds for indices in base cases are specified separately from recurrence bounds (e.g. base cases include index $0$, while recurrence indices start at $1$).
  • Directionality of Table Fill: The bounds convey directionality. A range $0 \le i \le n$ assumes a left-to-right fill order. If an approach depends on a right-to-left fill order (common for suffix-based approaches), bounds must reflect this (e.g. $n \ge i \ge 0$).
  • No Multiple Contradictory Definitions: In mathematics, you cannot say "$x = 5$" and "$x = 3$" simultaneously. Conditions must be mutually exclusive; otherwise can specify all remaining cases.
  • Single Value per Cell: A mathematically defined table entry can only take one value. In LCS, $L(0, 7)$ is defined under base cases, and $L(1, 5)$ is defined by the recurrence. (Exception: overlapping base cases like $L(0, 0) = 0$ are fine as long as they evaluate to the exact same value).
  • No Overwriting / No Imperative State: Table entries cannot be "overwritten". While updating variables is standard in procedural pseudocode with "before", "after", and "iterations", these concepts do not exist in mathematical recurrence definitions. A cell is a single immutable mathematical value.
  • Well-Defined References: Every table entry referenced on the right-hand side must have a clearly defined value. There must be no scenario where an out-of-bounds or undefined entry is evaluated.

3. Examples: Common Formulation Errors & Corrections

Example 1: Base Case Overlaps & Loop Constructs

Incorrect Version 1 (Overlapping Entries):

Base Case: $T[i] = 0, \ 0 \le i \le n$

Recurrence: $T[i] = T[i-1] + 1, \ 1 \le i \le n$

What's wrong: Multiple assignments to the same elements. All entries $1 \dots n$ are defined twice with contradictory values.

Incorrect Version 2 (Incomplete Bounds & If Statement):

Base Case: $T[0] = 0$

Recurrence: if i >= 1: T[i] = T[i-1] + 1

What's wrong: Incomplete bounds for $i$ (tables are finite, so an upper bound is required), and procedural if statement instead of mathematical specification.

Incorrect Version 3 (Procedural Loop Pseudocode):

Base Case: for i = 0 -> n: T[i] = 0

Recurrence: for i = 1 -> n: T[i] = T[i-1] + 1

What's wrong: This is completely procedural code with for loops and reassignment, not a mathematical definition.

Corrected Version 1:

Base Case: $T[0] = 0$

Recurrence: $T[i] = T[i-1] + 1 \quad ext{for } 1 \le i \le n$

Example 2: Self-Referential Definitions

Incorrect Version (Self-Reference):

Base Case: $T[0] = 0$

Recurrence: $T[i] = \max\{T[i], T[i-1] + 1\} \quad \text{for } 1 \le i \le n$

What's wrong: $T[i]$ appears on both the left and right sides of the equation. An undefined $T[i]$ is being used to define itself. This attempts to treat $T[i]$ as an accumulator variable in procedural code, which is illegal in a mathematical recurrence.

Corrected Version 2:

Base Case: $T[0] = 0$

Recurrence: $T[i] = \max_{0 \le j < i} \{T[j] + 1\} \quad \text{for } 1 \le i \le n$

Note: Helper indices like $j$ may be introduced to access earlier table entries as long as they are clearly bounded.

Acceptable Range Notations

Any of the following notations are acceptable for specifying ranges in your equations:

  • $T[i] = 0, \quad 0 \le i \le n$
  • $T[i] = 0 \quad ext{where } 0 \le i \le n$
  • $T[i] = 0 \quad ext{for } 0 \le i \le n$

4. Frequently Asked Questions (FAQ)

  1. Q: Should table entries use brackets [] or parentheses ()?
    A: Either is fine (e.g. $T[i]$ or $T(i)$), just remain consistent throughout your solution.
  2. Q: Would you define an empty set/list/array as {}?
    A: Yes, {} or $\emptyset$ is standard notation. Avoid obscure Greek symbols in Canvas text inputs due to formatting issues in the grading portal.
  3. Q: Can a base case be a non-discrete recurrence, such as $T[i, 0] = T[i-1, 0] + 1$?
    A: No. Base cases are expected to be terminating conditions that do not use recursion to produce an answer (i.e. explicit constants or hard-coded boundary values).
  4. Q: Are we allowed to use logical operators ("or", "and", "||", "&&", "!", "infinity") in our recurrence?
    A: Yes, standard mathematical or logical operators are fully permitted.
  5. Q: When is it ok to use "if" and not ok to use "if"?
    A: You can use "if" for conditional branches specifying piecewise definitions (e.g. on the right-hand side of a brace). You cannot use an imperative if (...) statement as program control flow.
  6. Q: If we use multiple tables, should each table have its own recurrence definition?
    A: The recurrence section is composed of base cases and general recurrence; both tables must fit cleanly into this unified structure. (Note: While using multiple tables can be valid, it is almost always more complicated than necessary for this course).

Exam Guidance: Follow the examples above and those in official homework solutions. If multiple acceptable notations are demonstrated, any of them will receive full credit.

Discussion Key Takeaways & Staff Clarifications

10 discussion threads • Staff rulings
  • Redundant Base Cases Are Harmless: Providing a base case that is technically redundant (e.g. defining both $T[0] = 0$ and $T[1] = a[1]$ when the general recurrence already yields $T[1] = a[1] + \max(0, T[0])$) will NOT lose credit on exams, provided it is mathematically correct and non-contradictory.
  • Overlapping Base Cases at Boundaries: Defining overlapping base cases like $L(i, 0) = 0$ for $0 \le i \le n$ and $L(0, j) = 0$ for $0 \le j \le n$ is fully acceptable because both assign the identical value $0$ at cell $(0, 0)$.
  • Range & Condition Phrasing: Prefer writing $ ext{"for } 0 \le i \le n ext{"}$ or $ ext{"where } 0 \le i \le n ext{"}$. Avoid using $ ext{"s.t."}$ (such that) for index boundaries, as mathematicians reserve "s.t." for set-builder or existential logic.
  • Compound Interval Bounds: Compound inequality bounds such as $1 \le i < j \le n$ are completely valid and standard for 2D interval DP (e.g., Chain Matrix Multiplication or substring problems).
  • Auxiliary Tables for Solution Reconstruction: Tracing backward through the computed DP table is standard. If you introduce a secondary backpointer table (e.g. $K[i, j]$ recording the optimal split point $k$), you must explicitly define its recurrence and account for its memory footprint.
  • Diagonal Evaluation Order (CMM): When table cells are filled diagonally by interval length $s = j - i$, describe the iteration order explicitly: "Iterate difference $s = 1 \dots n - 1$, then row $i = 1 \dots n - s$, setting column $j = i + s$."
  • Empty Set Maxima: By course convention, $\max(\emptyset) = 0$. Stating this convention explicitly or writing $\max(\{0\} \cup \{\dots\})$ prevents grading ambiguity.
